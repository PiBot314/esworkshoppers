## 3. A5: per-row quantization of the LSTM weights ✅ (emulator)

Answered from the 19 Nov builds, no new run needed: with `--use_per_row_quantization` the converter gives **all four
expanded LSTM weight matrices 384 per-row scales** (row-scale spread 2.5–4.8×) instead of one per tensor; that build
(with `--enable_per_row_quantized_bias`) is the 45.2 dB one. So a fused (stacked) LSTM keeps a scale per row, i.e. per
model. Still to confirm on the board.

* Weather forecasts help the LSTM at 24 h (+0.016 solar, +0.020 grid) and not at 1 h, the same pattern as LightGBM.
* LSTM ≈ LightGBM for solar (0.814 vs 0.815 at 24 h); **LightGBM is better for grid 24 h (0.870 vs 0.804)**.
* Guided gate ≥ unguided in all 4 comparisons (+0.003 to +0.008).
* **Pre-training on the simulated years does not help** (−0.008 to −0.019). Follow-up
  ([b3_pretrain_check.py](../../forecast_2025/b3_pretrain_check.py), solar 24 h): 0 / 1 / 2 pre-training epochs at full
  fine-tune lr → validation MSE 0.0175 / 0.0179 / 0.0186, test R² 0.814 / 0.809 / 0.800: monotonically worse, so chosen
  on validation = none. Likely reasons: the simulator's day-to-day weather link is weak (daily R² ≈ 0.57, ERA5-limited),
  and pre-training feeds ERA5 where the real model gets forecasts. Documented as a negative result; the simulated set
  stays for climatology-style uses.

## 6. C1: fusion tooling ✅ (accuracy in the emulator; timing needs the board)

* [forecast_2025/c1_fuse.py](../../forecast_2025/c1_fuse.py): K models with the same 96-step window (any input width or
  horizon) → one ONNX graph: one 2-layer LSTM with block-diagonal weights per gate, each head reading its slice of the
  hidden state. FP32 outputs identical to the separate models (max diff 0.0 on random inputs).
* [forecast_2025/c1_emulator.py](../../forecast_2025/c1_emulator.py): real test windows → QNN W8A16 per-tensor vs per-row
  (+bias flag) → x86 HTP emulator → SQNR per fused model vs FP32.

**C1 results** (x86 HTP emulator, W8A16, plain QNN calibration on 100 validation windows, SQNR vs FP32 on 50 test
windows; each model scored on the same windows fused and alone; `forecast_2025/fused/*.emu.json`):

| Graph | Model | per-tensor | **per-row (+bias flag)** | same model alone, per-row |
|---|---|---|---|---|
| solar 1 h + 24 h (hidden 128) | solar 1 h | 43.5 | **52.9** | 49.4 |
| | solar 24 h | 42.0 | **46.5** | 46.4 |
| all 4 (hidden 256, inputs 8+8+15+15) | solar 1 h | 46.3 | 55.5 | 49.4 |
| | solar 24 h | 42.1 | 46.5 | 46.4 |
| | grid 1 h | 24.4 | 24.1 | 34.5 |
| | grid 24 h | 29.6 | 29.3 | 37.2 |

* **Solar: fusion is free and per-row is what passes the ≥ 44 dB gate** (per-tensor 42–43.5 fails for 24 h). One
  graph, one call, one 128-wide multiply per LSTM step instead of two 64-wide ones.
* **Grid: below the gate even alone (34–37 dB), and worse fused (24–30 dB).** Per-row doesn't change it, so the loss
  is in the activations, not the weights. *(Second pass, §8: the cause was a calibration set with no holidays; fixed.
  Also corrected: QNN's ONNX simplifier failed on **all** graphs, solar included — `onnxsim` can't import with the
  container's numpy — not on the grid graphs only.)* These builds use plain calibration, not the October recipe (fixed ±1 ranges for LSTM
  states, AdaRound), which took the old LSTM from 44 to 77 dB. **Rule for now:** fuse within a family (solar 1 h +
  24 h); keep grid separate until it passes alone with the October recipe (B5).
* Timing (one fused call vs separate calls; batching over plants, C2) needs the board.

## 8. Second pass: fixing the evaluation ✅ (mostly)

The first pass looked like "little improvement anywhere". Reviewing it found five problems with how it was measured,
not only with the models: B2 and B3 were scored on different rows; no uncertainty on differences of 0.01; the
deployed models were never scored on the 2025 test weeks; one average hid where weather matters; the LSTM had no
rolling-origin run. Details and all tables: [forecast_2025/README.md](../../forecast_2025/README.md).

* **E1, identical rows + 95 % CIs** ([forecast_2025/e1_compare.py](../../forecast_2025/e1_compare.py)):
  * **New vs deployed:** grid 1 h LightGBM 0.931 vs live model 0.862 (+0.069 [+0.050, +0.098]); the live model is no
    better than persistence (0.866). Grid 24 h LightGBM 0.873 vs best deployed 0.660 (+0.21; +0.14 on the 3 weeks the
    deployed weights never saw). Campus solar: new LSTM +0.038 (1 h) / +0.047 (24 h) over the best deployed model.
  * **Weather** helps at 24 h (LightGBM solar +0.055 [+0.016, +0.107], grid +0.029), not at 1 h, where B2's
    perfect-weather runs show there was no room. At 24 h the solar gain is on clear days.
  * **LightGBM beats the LSTM on grid** at both horizons (significant); they tie on solar.
  * **Guided gate** significant only for grid 1 h (+0.019); **pre-training** no benefit (CIs include 0).
* **Grid v2** (day/week-ago covariates in the LSTM head, then a skip connection): grid 1 h +0.006; grid 24 h −0.024
  (n.s.). The hypothesis that the missing weekly lag caused the LSTM–LightGBM gap is **rejected**.
* **E2 rolling-origin** ([forecast_2025/e2_rolling.py](../../forecast_2025/e2_rolling.py)): grid 1 h LSTM 0.784 vs
  LightGBM 0.888; with 1–3 months of history the LSTM is at 0.45–0.54, LightGBM 0.75–0.83. The LSTM is data-hungry.
  Solar: 1 h LightGBM 0.802 vs LSTM 0.783 (significant), 24 h 0.744 vs 0.751 (tie); weather +0.05–0.06 at solar 24 h.
  Over all 8 comparisons LightGBM is significantly better in 4 and tied in 4. Blending the two helps only grid 24 h on
  unseen months (+0.034).
* **Grid quantization fixed in the emulator:** the error sat in a few windows (holiday, long gap) that the 100 val
  calibration windows never covered. Calibrating on 500 train + val windows: grid 1 h per-row **34.7 → 51.3 dB**
  (passes 44 dB); grid 24 h **37.6 → 48.6 dB**. Fused with the solar models (all 4, same calibration) grid is still
  19–26 dB (shared activation scales), so the fuse-within-a-family rule stands. Solar 1 h's 40.7 there is the
  calibration, not grid: fused solar with the wide calibration is 40.8 / 49.5 vs 52.9 / 46.5 with 100 val windows, so
  calibration is chosen per family. Board packages built: `fused/solar_1h24h_board/`, `fused/grid_1h_v2_cal500_board/`.
* **M4: API-fitted grid limits applied** to all 6 models' `meta.json` ([datasets/api_2026/apply_api_limits.py](../../datasets/api_2026/apply_api_limits.py);
  2025 limits kept as `anomaly_2025`, `--undo` restores). Takes effect on the next push to the board.
