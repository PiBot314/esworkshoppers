* The board couldn't reach the API from **18 Nov 13:00 to 19 Nov ~13:25**. The loop logged timeouts (not "network

## 3. `qnn-net-run` crashes and the catch-up fix

**Finding:** 204 crash reports (SIGSEGV) from the one-shot `qnn-net-run` since 16 Nov (45 on 16 Nov, 62 on 17 Nov,
97 during this catch-up), none from the resident runners.
* Each crash is in a `HwBinder` thread, ~2 s into the run, at an address with no code loaded: a race while the process
  shuts down, after its output is written. Eight manual runs on the board all exited cleanly with identical output.
* **No forecasts were lost** (§2); `nz_dashboard` reads the output file and ignores the exit code. Not fixable on our side
  (Qualcomm's binary); avoided by not using the one-shot path.

**Why catch-up used the one-shot path:** the runners are warmed 20 s before each cycle and exit after 45 s idle. After an
outage the cycle first downloads the missed day, which outlasted that, and `catchUp()` never warmed them again.

**Fix:** `catchUp()` now calls `warm(90)` first ([loop.ts](../../qidk_export/dashboard/src/lib/server/live/loop.ts)).
* A2 replay unchanged: Grid 41/41, PL00 12/12, injected 20/20.
* Catch-up test against the board's NPU (95 missed bins, runners cold): **56.8 s** instead of ~11 min, all 7 runners
  resident, every shadow forecast present, **0 new crash reports**
  ([catchup_test.ts](../../benchmark_qidk/live_eval_2026-11-19/catchup_test.ts)).
* Deployed 13:56; the 14:02 check ran normally.

## 4. USB fallback route to the API

* The live loop now has an ordered list of routes: direct over Wi-Fi, then `http://127.0.0.1:19999` on the board →
  `adb reverse` over the cable → a `socat` relay on the laptop → API. It probes them at the start of every cycle and
  uses the first that answers. Laptop side: [usb_uplink.sh](../../nz_live/laptop/usb_uplink.sh) as the systemd user service
  `nz-usb-uplink.service` (installed and enabled). Details and commands: [SYSTEM_DESIGN.md](../../SYSTEM_DESIGN.md) §9a.
* The USB route isn't affected by Docker's forwarding drop (the laptop makes the API connection itself). It still needs
  the laptop awake.
* **Tests:** A2 unchanged; direct refused → USB in < 1 s, silent → USB after ~7 s, working → direct.
* **Real switchover:** the laptop was moved and joined `wifi@iiith` as a client, which turned the hotspot off. The board
  lost Wi-Fi; after the deploy (~15:00) the loop picked USB, caught up the 2 checks missed during the move, and kept
  running (NPU 3.9 ms). The Live page shows "Campus API reachable · USB (via laptop)".
* Side effect while the board has no Wi-Fi: its clock falls back to 2023 (no network time). Forecasts are unaffected
  (the loop uses the API clock); board log timestamps are wrong.
* `start.sh` now lists both routes (`LIVE_API`); `loop.ts` also appends the USB route itself unless `LIVE_USB=0`.

**Campus Wi-Fi for the board (open):** from the board's position, `wifi@iiith` is WPA2-Enterprise (personal login)
with a weak signal (−74 to −76 dBm); `esw-m19@iiith` (WPA2-PSK, likely the course network) is strong (−36 dBm). If
either reaches 10.2.x, the board wouldn't need the laptop at all. Personal credentials shouldn't go through scripts or
chat: enter them on the board's Settings screen (or via `scrcpy`), or use the course network's shared password.

## 5. NPU vs CPU on the live system (partial)

Scripts and raw output: [benchmark_qidk/live_eval_2026-11-19/](../../benchmark_qidk/live_eval_2026-11-19). The run was
stopped early, after the project's goals for the NPU were restated (§7); numbers below are what was measured.

| Per check (7 models, one window each) | Idle board | Assistant generating |
|---|---|---|
| NPU, including starting the 7 runners | 10.8–10.9 s (10 runs) | 23.1–28.5 s (2 runs) |
| CPU, ONNX Runtime FP32 1 thread, load + 1 run per model | 51–78 ms (10 runs) | 130–142 ms (2 runs) |

| Per window, start-up excluded | NPU W8A16 (resident runner) | CPU ONNX Runtime FP32, 1 thread |
|---|---|---|
| `all_sensors_1h` (deployed Grid) | ~5 ms (live loop: 2.5–6.9 ms) | 0.54 ms |
| `single_node` (Palash) | ~5 ms | 0.26 ms |
| `guided_h4` | 3–5 ms | 0.54 ms |

**Assistant speed** (1,176-token prompt, 200 tokens written): alone 78 / 10.4 and 70 / 9.5 tokens/s (prompt / answer);
next to a continuous NPU loop 70 / 9.6. The spread between the two "alone" runs (~10 %) is as large as the NPU effect, so
no conclusion yet; the CPU-loop comparison wasn't measured (`e3.py` is ready to rerun, ~10 min).

**Reading:** for these small LSTMs, one window at a time, the CPU is ~5–10× faster even without start-up (the NPU pays
~1.5 ms per call and runs the 96 LSTM steps one after another). Runner start-up (~1.5 s per model, CPU work) dominates
each check and slows ~2.5× when the assistant is busy: keeping the runners resident would remove it.

## 7. Direction discussed (proposals, not decided)

The project should show (1) the utility of the system and its ideas, (2) innovation and creativity, (3) an effective,
if somewhat forced, use of the NPU. Proposed, roughly in order:
1. **Measure the offload argument:** does forecasting on the NPU leave the CPU to the assistant while CPU forecasting
   slows it (rerun `e3.py`; plan W6.2).
2. **Fuse the same-shaped LSTMs into one graph** (`baseline_h4`, `guided_h4`, `baseline_24h`, `guided_24h`; maybe the
   deployed one): stacked weights, one wider step per time step, one call. Expected ≈ the time of one model. Check
   per-channel quantization accuracy. ~1 day.
3. **Batching across windows and campus nodes** (plan W6.1 + W2 shared per-family models + W4 per-node faults): where the
   NPU should overtake the CPU; report cost per node vs batch size, NPU vs CPU.
4. **On-device head refit** (plan W3): frozen quantized body on the NPU, last layer refitted on the CPU.
5. Assistant on the NPU (QAIRT Genie): feasibility study only; multi-day, risky.

Other ways to make the NPU faster, less promising: shared-memory input instead of files and HTP RPC polling settings
(trim the ~1.5 ms per call); NPU-friendly models (hourly 24-step inputs, convolutional instead of LSTM); W8A8 (~1 ms,
but hurt 24 h accuracy before).

## 7b. Per-channel quantization: root cause found (evening, no board needed)

October's 14.6 dB with per-channel dense weights was **our converter usage**: per-channel weight overrides on a
FullyConnected layer need `--use_per_row_quantization --enable_per_row_quantized_bias`; without the bias flag the 32-bit
bias keeps one scale while the weights are per-row, so each row's bias is mis-scaled (19.1 dB). With both flags: 45.2 dB.
Found with the SDK's x86 HTP emulator, which reproduces the board (50.1 dB for the deployed model vs 48.4 dB). An
intermediate conclusion (that the HTP backend mis-executes per-channel FullyConnected) was wrong and is corrected. Per-row
scales are therefore available for fusing models. Details: [plan_19112026.md](../plan_19112026.md) part A, "Result".
