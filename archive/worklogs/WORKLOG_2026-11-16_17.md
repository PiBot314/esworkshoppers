## Summary

**What now runs, unattended on the QIDK**, with the laptop only as a Wi-Fi hotspot:
* every 15 minutes, live campus API readings → forecasts on the Hexagon NPU → anomaly flags
* 7 switchable forecasting models, all of them running in shadow
* an on-board assistant that can explain flags, models and results
* a dashboard led by live NPU forecasting, with a Results tab that compares every model with simple baselines

It starts by itself at boot, survives power cycles, and catches up after outages.

**The most important finding:** on real 2025 data, "next reading = current reading" (persistence) beats every model 15 minutes ahead. The models add value only for **solar one hour ahead** and **grid one day ahead**. For 24 h solar, "same time yesterday" beats every model, because no model has weather inputs. This now shapes the plan.

## 2. Network and start-up (16 Nov)

* **Hotspot:** the laptop's existing `Hotspot` profile (`QIDK_DevNet`, 2.4 GHz, auto-connect, priority 100) with NAT to the wired `IIIT-LAN`. The laptop's own traffic stays on the wire.
* **Board on Wi-Fi:** joined through `adb root` (the shell user can't). Android had blacklisted the hotspot as "no internet", so its connectivity check was turned off (`captive_portal_mode 0`).
* **Board → API failed at first:** Docker 29 on the laptop sets the forwarding policy to DROP. Fixed with two `iptables` rules (user). **Still temporary:** the permanent `daemon.json` fix is pending.
* **Boot service:** `/system/etc/init/nz_live.rc` starts `start.sh` as `shell` at `sys.boot_completed`. Tested with a reboot and with a full power cycle (A5).
* **Dashboard deploys:** a script waits for USB, pushes the build next to the old one, swaps them, and restarts only the dashboard (the supervisor brings it back in seconds). Used for every deploy since.

## 4. Models: the switcher (17 Nov)

* **7 models for Grid** (the deployed `all_sensors_1h` plus `baseline_h4`, `guided_h4`, `baseline_24h`, `guided_24h`, `cnn_lstm_24h`), and `single_node` for Palash.
* **Getting the newer models' inputs right:** they expect the teammate's feature order (saved with the LightGBM model) and the data's capacities. A first attempt with the wrong order gave Solar R² 0.47 instead of ~0.96. Now verified against their own training results.
* **Per-model limits:** each model's per-hour median and limit are fitted on its own 2025 validation residuals with the same rule as the deployed one (`build_model_meta.py`).
* **On the board:** `nz_dashboard` reads a model registry. Every new model matches its FP32 output (**44.1–47.7 dB**) and runs in 3.1–5.0 ms on the NPU.
* **Switching:** from the Grid card; re-forecasts the last 24 h with the new model; survives restarts; the assistant can describe models (`list_models`) but never switch them. `cnn_lstm_24h` is **comparison-only** (Grid R² below zero).
* **Finding:** scored the same way at +15 min, the deployed model was already the best Grid model (0.824), so it stays the default.

## 5. Net zero page fix (17 Nov)

The page said +1,125 % solar would reach net zero but didn't show zero. Three causes, all fixed or labelled:
1. **"×" meant different things:** the headline meant *extra* solar and the slider meant *total*. Now both say "+X % more (Y× today's in total)".
2. **The headline assumed export; the slider didn't.** Added a **net-metering switch**. With it on, +1,225 % reaches zero (−0.57 t). With it off, the page says plainly that solar alone can't: night-time load keeps net emissions above ~1,118 t however many panels are added.
3. **"Today's solar" counts only 3 meters**, so the multiples are overestimates. Now labelled on the page; the proper fix (one solar basis everywhere) is still open.

## 6. Persistence test, Results tab and shadow mode (17 Nov)

**The test** (prompted by an outside review). Same windows for every model, R²:

| 2025 test split | Solar: best model | Solar: best baseline | Grid: best model | Grid: best baseline |
|---|---|---|---|---|
| +15 min | 0.966 | **0.978** persistence | 0.936 | **0.937** persistence |
| 1 h | **0.953** (guided LSTM, skill +0.45) | 0.916 yesterday | 0.856 | **0.864** persistence |
| 24 h | 0.800 | **0.915** yesterday | **0.198** (LightGBM) | −0.05 yesterday |

On the synthetic API the ranking depends on the period. Over 16 replayed days, several models beat persistence on Grid (best +0.19); over the last 24 h live, none did. Palash's model beats persistence in both windows (+0.32).

**What was built:**
* **Shadow mode:** every Grid model that isn't active forecasts each reading too (own limits, never alerted), and persistence and same-time-yesterday are scored for both signals (`shadow.jsonl`, 8 days).
* **Results tab:**
  * a verdict per horizon;
  * all models × baselines with skill;
  * the live scoreboard (24 h / 3 d / 7 d);
  * LightGBM's input importance (time features ~58 %, substation ~17 %);
  * per-hour allowed deviation.
* **Assistant:** a `model_results` tool. Its first answer got 24 h grid wrong, so the tool's findings are now one explicit sentence per horizon.

## 7. Resident NPU runner (17 Nov)

* **What:** Qualcomm's SDK SampleApp, extended with a request loop that keeps the finalized graph (`nz_live/runner/nz_runner`). `nz_dashboard` starts one per model on request (`/api/warm`), feeds it windows, and stops it when idle.
* **Timing:** the live loop warms the runners **20 s before each check**, and they exit **45 s after the last request**, so the NPU and memory are free between checks.
* **Result:** ~1.8 s start-up per model once per check, then **~3–5 ms per window** instead of ~1.8 s, with identical output (47.5 dB vs FP32). 24 h backfill of 7 models: 480 windows in ~44 s (was ~6 min for 192).

## 8. Catch-up after outages (17 Nov)

After an outage or a restart, the loop checks every missed 15-minute bin (up to 24 h) as the live cycle would have. Flags found this way are events marked **late**: no banner, shown as "found after an outage". The last checked bin is saved, so restarts are covered too.

Tested: A2 only. **Not yet tested with a real outage**, and no outage log in the UI yet.
