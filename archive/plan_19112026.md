## 2. Part A: the per-channel experiment (~1 h)

**Known** (deployment log, failure #6, in [mideval_md/explanation.md](../mideval_md/explanation.md) §7.2): with per-channel
encodings on the two dense layers (`fc1` 48×96, `fc2` 12×48, axis 0), the AIMET W8A16 model gave **14.6 dB** on the
NPU; with only those encodings removed, **46.2 dB**. The ONNX side is correct: both layers are `Gemm` with
`transB=1` and weights `[out, in]`, so axis 0 is the output-channel axis. The fault is downstream, and was never
root-caused.

**Hypotheses, most likely first:**
1. The QNN converter turns `Gemm` into a fully-connected op and transposes the weight, but doesn't move the per-channel
   scales to the matching axis (48 scales applied along a 96-wide axis).
2. The HTP backend in QAIRT 2.47 doesn't properly support per-channel weights for this op.
3. AIMET 2.12's per-channel entries don't match what QAIRT 2.47 expects in the encodings file.

**Steps:**

| Step | What | Time |
|---|---|---|
| A1 | Copy the deployed `all_sensors_1h` encodings (`aimet_quantization/out/all_sensors_1h/final/`); replace only `fc1.weight` and `fc2.weight` with per-channel symmetric 8-bit scales computed from the FP32 weights (one per output row). No AIMET run, so it's the deployed model except for two tensors | ~10 min |
| A2 | Convert and compile with `scripts/08_qairt_build.sh` (qairt-fixed:2.47 container) | ~5 min |
| A3 | Read `fc1.weight`'s quantization parameters in the generated `*_net.json`: which axis, how many scales, in which order | ~5 min |
| A4 | On the board, between live checks: one window with `qnn-net-run --debug` on the NPU and FP32 on the CPU; compare `fc1`'s and the final output tensors (SQNR); also the full SQNR on 600 validation windows if A4 passes | ~10 min |
| – | Margin for snags (encodings format, script flags) | ~20–30 min |

**Outcomes and what follows:**

| Result | Meaning | Next |
|---|---|---|
| A3 shows the wrong axis | Hypothesis 1 | Workaround: export dense layers as `MatMul` with a pre-transposed weight (no conversion transpose); retest. If it works, per-channel is usable for dense layers |
| A3 axis right, A4 output wrong | Hypothesis 2 or 3 | Per-tensor stays; fusion uses the fallbacks in C1 |
| A4 ≥ 46 dB | October's problem was in AIMET's export, not the NPU | Use per-channel for dense layers in the new models (B5) |

**A5 (optional, ~1–2 h, only if A works):** the same test on the **LSTM** weights. With `--expand_lstm_op_structure`
the LSTM becomes `MatMul`s on the NPU, and fusing models stacks exactly these weights (C1). In October AIMET crashed
when asked for per-channel on a constant-folded LSTM weight, so A5 also writes those encodings by hand. Its result
decides whether fused models can keep a scale per model.

**Deliverable:** a short section in the worklog with the root cause (or the remaining hypotheses), and the rule for B5.

**Result (19 Nov, done without the board; corrected the same evening).** The QAIRT SDK's x86 emulator of the HTP
backend reproduces the board (deployed model 50.1 dB on 20 test windows vs 48.4 dB on the board), so A4 ran on the laptop.

| Dense layers as | Converter flags | SQNR vs FP32 (HTP emulator) |
|---|---|---|
| `Gemm`, per-tensor (deployed) | – | 50.1 dB |
| `Gemm`, per-channel overrides | – (as in October) | **19.1 dB** |
| same | `--use_per_row_quantization` | 19.2 dB |
| **same** | **`--use_per_row_quantization --enable_per_row_quantized_bias`** | **45.2 dB** |
| `MatMul` + `Add`, per-channel | – | 19.1 dB (converted to FullyConnected) |
| 1×1 `Conv`, per-channel | – | 46.3 dB |

* **Root cause: our usage, not Qualcomm's backend.** A FullyConnected bias is stored as 32-bit integers with scale =
  input scale × that row's weight scale. Without `--enable_per_row_quantized_bias` the converter keeps one bias scale
  (per-tensor assumptions) while the weights are per-row, so each row's bias is mis-scaled. With the flag, per-row
  FullyConnected runs correctly on HTP. (An intermediate conclusion that the backend was at fault was wrong.)
* Usability feedback worth giving Qualcomm: the converter silently accepts per-channel weight overrides on
  FullyConnected and builds a mismatched bias, without a warning.
* 45.2 vs 50.1 dB because the deployed weights were AdaRound-tuned for the per-tensor scale and the per-row scales were
  recomputed without AdaRound; not a like-for-like accuracy comparison.
* **Rule for B5:** per-row is available for dense layers with both flags. **For C1 (fusion):** the expanded LSTM's gate
  multiplies are FullyConnected too, so stacked models can keep a scale per model (per row) with the same flags; A5
  should confirm on the LSTM weights.
* Files: `aimet_quantization/out/all_sensors_1h/{perchan,perchan_mm,perchan_conv,qnn_perchan,emu}/`;
  `aimet_quantization/scripts/perchannel_variants.py`. Accuracy checks run on the laptop via the emulator
  (`qnn-model-lib-generator -t x86_64-linux-clang`, `qnn-net-run --backend lib/x86_64-linux-clang/libQnnHtp.so`).

## 3. Part B: the new model (~7–9 days)

**Decisions, 19 Nov evening:**
* **Option C:** weather-aware models are trained and evaluated on **real 2025 data only** (real 2026 slots in if the lab
  exports it). The API's 2026 history is used only to calibrate the live system on the data it actually sees: alarm
  limits fitted on API data (M4), shadow-score norms, fault-injection replays, and the real-vs-API behaviour gap.
* **Multiple years of weather** (ERA5 2015–2024, downloaded): (1) climatology features, i.e. how cloudy/hot today is
  relative to the 10-year normal for the date; (2) **simulated-plant pre-training**: fit output ≈ k × irradiance per
  plant on 2025, generate ~10 years of simulated output from historical weather, pre-train the solar model on it,
  fine-tune on real 2025; evaluated with and without pre-training.
* **Data handling learnt today:** 6 of 9 real solar plants usable (not PL96, VN02-00, VN03-00); units differ
  (`ActivePower` W, `3_Active_power` kW); Palash reports negative; VN95 has a night offset; timestamps are Unix
  seconds → IST (verified against the sun); every source on the "mean over the interval ending at the stamp" convention.
* **Solar target as clear-sky index** (output ÷ clear-sky, per kWp), and a new solar baseline: clear-sky-index
  persistence. Weather inputs: `previous_day1` (24 h) and 15-min historical forecasts (short horizons); ERA5 only as the
  "perfect weather" upper bound.

**Design, fixed up front:**
* **Template:** the guided LSTM from [common/train_fair_lstm.py](../common/train_fair_lstm.py) (gate fused into
  `weight_ih` at export), one shape per family, 96 × 15-min input window.
* **Families:** solar (per plant, output per kWp), grid / building load. Water and AC stay as profiles
  ([plan_integrated.md](plan_integrated.md) §8 #6). "Demand" (KH04) dropped as a target.
* **Nodes:** only API-served nodes and inputs; one shared model per family, nodes as the batch; static node features
  (capacity, orientation) where available.
* **Inputs:** past window (sensor values, time features) + **future covariates for the forecast horizon**: weather
  forecast (shortwave radiation, cloud cover, temperature), clear-sky irradiance (pvlib), campus calendar. Future
  covariates enter the dense head, so the LSTM body is unchanged.
* **Horizons:** 1 h (4 steps) and 24 h (96 steps); report 1 h, 6 h, 24 h.
* **Export:** split into body (LSTM, NPU) and head (dense, CPU or NPU) for the on-board refit (W3), with a **batch
  dimension** for nodes (C2). `meta.json` holds the feature order, scaling, data version, node list and capacities.
* **Training:** on the laptop GPU (RTX 3050 Ti).
* **Splits (both, reported side by side):**
  * **Blocked-random weeks with gaps** for training and model selection: whole weeks assigned at random to train /
    validation / test (70 / 15 / 15), with a gap of at least window + horizon (~2 days) between a training week and an
    evaluation week. Every season is in every set and no window is shared. Not random *points*: windows 15 min apart
    share 95 of 96 steps, so a random-point split tests on near-copies of training data.
  * **Rolling-origin** for the headline: train on months 1..k, test month k+1, for every month. Matches deployment
    (past → future) and gives per-season scores.
  * The gap between the two is reported as a result (how much unseen seasons cost; motivates W3 adaptation).
    Optional: one run with a random-point split, labelled leaky, to show the inflation.
  * The current models used a chronological 70/15/15 split of 2025 (`common/common_data.py`), so their test period
    (≈ mid-Oct to Dec) is a season they never trained on. Keep that in mind when quoting their scores.
* **Data sources (corrected 19 Nov evening):** the mentors' API history for 2026 is **synthetic and not driven by real
  weather**: its solar output has a realistic day shape, season and level (94 % of real 2025), but its day-to-day
  variation is unrelated to the weather (daily output vs ERA5 irradiance r = 0.21 for 2026, no month above 0.46; vs
  2025 by day of year r ≈ 0.37; not a shifted copy of 2025). Control: **real 2025** Palash vs ERA5 r = 0.80 daily, 0.83
  hourly. The API's weather station `WE-VN04-00` is synthetic too (daily r 0.23 vs ERA5). Consequences:
  * **Weather-aware models are trained and evaluated on real data only:** the 2025 dump (`datasets/esw/`) and real
    2026 if the lab exports it. On API data weather inputs can't help, and the live board can't show a weather gain.
  * API history is useful for the live system's behaviour (shadow scores, limits fitted on API data, fault-injection
    replays), not for weather experiments.
  * Real 2025 data checks the weather sources: ERA5 r = 0.80 and historical forecast r = 0.79 vs Palash daily output.

**Steps:**

| Step | What | Days | Gate to the next step |
|---|---|---|---|
| B1 | **Data.** List API-served nodes and inputs per family; rebuild the 2025 dataset from them; per-kWp normalisation; versioned scaling; download Open-Meteo **historical forecasts** for the campus and align them to the 15-min grid; pvlib clear-sky; campus calendar from the academic calendar | 2 | Coverage of the archived forecasts for 2025 known (if partial: reanalysis archive, skew stated); dataset reproducible from a script |
| B2 | **Feature test with LightGBM.** Train LightGBM with and without the new features per family and horizon (minutes per run). Gives the first answer on whether weather and calendar help, and the importances for the guided gate | 0.5 | At least one horizon improves over the current best, or a documented "doesn't help" |
| B3 | **Model.** Guided LSTM template with future covariates in the head; per-family shared model over nodes; split export with batch dimension | 2–3 | Trains stably; matches LightGBM's ranking of feature groups |
| B4 | **Evaluation grid.** {no weather, clear-sky only, clear-sky + forecasts} × {1 h, 6 h, 24 h} × family; blocked-random and rolling-origin (both reported); R², nMAE, skill vs persistence and same time yesterday; per-node and per-season results | 1–2 | **24 h solar above 0.915** (same time yesterday); 1 h solar not worse than `guided_h4` (0.953); grid 24 h above LightGBM's 0.198 |
| B5 | **Deploy.** W8A16 with the October recipe (fixed ranges, AdaRound, per-tensor, or per-channel for dense layers if A says so); verify on the board (SQNR vs FP32 ≥ 44 dB, flag agreement); add to the registry; run in **shadow mode** before promoting | 1 | Board SQNR ≥ 44 dB; a week of shadow results; promotion is manual |

**Risks:**
* Open-Meteo's historical forecasts may not cover all of 2025 → reanalysis archive, with the skew stated.
* Few API-served nodes per family → pooled training may still be thin; node features become more important.
* Weather helps LightGBM but not the LSTM → ship LightGBM on the CPU for that horizon, and say so (W2 distillation as
  the follow-up).
* The board needs internet for live weather forecasts → fetched through the laptop, cached, and the live loop falls
  back to the clear-sky-only model when the cache is stale.

## 4. Part C: NPU use of the new models (~2–3 days, after A and B)

**C1. Fusion.** Same-shaped models (e.g. the 1 h and 24 h variants, or several families) stacked into one wider graph:
one call per check instead of one per model, and one wider multiply per LSTM step instead of several small ones.
Expected: about the time of one model.
* If A5 works: stack the weights and keep a per-channel scale per model.
* If not: stack and measure (models trained alike likely have similar weight ranges), or keep each model's weights as
  separate tensors in one graph (one call, so the per-call overhead is paid once, but no wider multiply).
* Check: SQNR per fused model vs its unfused version; NPU time per check.

**C2. Batching.** The per-family models over all API-served nodes in one call. Measure cost per node against batch size
(1, 2, 4, … nodes), NPU vs ONNX Runtime on the CPU, with the assistant idle and busy. This is where the NPU should
overtake the CPU; the crossover point is the result.

**C3. Keep runners resident.** Starting runners costs ~10.8 s of CPU per check now (WORKLOG §5). With fused and
batched models there are 1–3 runners, so keeping them resident permanently becomes cheap.
